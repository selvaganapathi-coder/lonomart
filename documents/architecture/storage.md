# Storage Architecture

Cloudflare R2 is documented as the future asset store. No R2 client code or bindings are implemented in TASK-001.

## Bucket strategy

Start with a small number of environment-specific buckets, such as one production bucket and one non-production bucket, configured outside source control.

## Object naming strategy

Use server-generated object keys in this pattern:

`websites/{websiteId}/assets/{assetId}/{safeFilename}`

Never trust a client-provided object path for authorization.

## Website ownership

Every asset must be associated with a website record and owner/tenant metadata in the database before upload or read access is granted.

## Asset metadata

Future metadata should include asset id, website id, original filename, safe filename, content type, size, checksum when available, creator id, timestamps, and visibility.

## Secure upload approach

The server should authenticate and authorize the request, create the asset record, generate the R2 object key, and only then issue a constrained upload path or signed URL.

## Public/private access strategy

Private source assets should remain non-public by default. Published assets can be exposed through a controlled public URL or CDN path only after publication rules authorize them.

## Future direct-upload architecture

Direct browser uploads should use short-lived, scoped credentials or signed URLs for a single object key generated by the server. R2 credentials must never be exposed to browser code.
